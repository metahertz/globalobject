# ZFS-only interface grows code, shrinks resilience

**Making ZFS send/receive streams the only way users put data into GlobalObject would not simplify the codebase. It would delete about 340 lines of client code and 70 dependency packages, then add an estimated 1,300 to 2,600 new lines (central estimate about 1,700), for a net growth of roughly 1,000 to 2,200 lines** ([codebase audit](../research_notes/ZFS%20send%20receive%20only%20interface/codebase_audit.md)). The CAP class stays the same: the MongoDB control plane is already consistent-and-partition-tolerant (CP) for grants and commits. But correctness would then depend on a linearizable compare-and-swap on a per-chain head, where today a grow-only set of immutable objects only needs each insert to be atomic. Durability changes in shape rather than average. The expected bytes lost per year stay similar, but one lost segment in a full stream makes every snapshot built on it unrestorable. With 30 daily incrementals on a 1 TiB base, that is about 89% of the chain's snapshots, and the chance that a chain breaks within a year is about 6% at the simulator's 1-of-3 loss rate. Restic would instead lose a few megabytes of individual files that can be repaired. Single-file restore stops being possible: a 20 KB file would cost about 1.3 TB of granted reads and six days instead of 38 KB. **Recommendation: do not replace the restic client. If ZFS users matter, add ZFS streams as a second, opt-in input in phases**, starting with a stream-into-restic stopgap that needs no control-plane changes. Then build a native stream path with bounded full/diff/incr chain depth, client-side AEAD over every stream, and a chain-head compare-and-swap in MongoDB, for roughly 9 to 14 engineer-weeks, plus 1.5 to 2.5 weeks of prerequisites (mainly the delete grace window, which the project needs anyway). That figure is an engineering judgement, not a measurement.

Method: this report synthesises four research notes written on 2026-11-20, plus earlier work on ZFS licensing and encryption. Line and package counts were measured with `wc -l` and a script over `Cargo.lock`. Availability, durability and storage figures come from a binomial and Poisson model whose inputs are assumptions (64 MiB segments, 1% daily change, 80/90/95% host uptime). They are not measurements. Effort estimates are judgements scaled from comparable existing code.

## The restic dependency is narrow, so removing it saves little

All of the format-specific code sits in one crate. `rustic_core`, `jiff` and `bytesize` appear only in `crates/client/Cargo.toml`. Outside it, restic shows up in one constant in the control plane (`OBJECT_TYPES = ["config","index","key","snapshot","pack"]`) and in one doc comment ([crates/control-plane/src/api.rs](../crates/control-plane/src/api.rs), [crates/client/src/lib.rs](../crates/client/src/lib.rs)). The other nine crates work on opaque ciphertext and would carry over unchanged. They cover segmenting, erasure coding and local parity, the node, iroh transport, policy, the simulator, and the control plane's placement, grants, quota, ledger, audits, repair and drain. Together that is **about 6,000 of the workspace's 8,888 lines of Rust**. The node's own doc comment states the boundary: "Repair works on ciphertext alone" ([crates/node/src/lib.rs](../crates/node/src/lib.rs)).

The dependency is narrow but load-bearing. The client's module doc says "Encryption, chunking, dedupe, compression and snapshots all come from `rustic_core`". `crates/crypto` encrypts no data at all: "File encryption lives in `rustic_core`" ([crates/crypto/src/lib.rs](../crates/crypto/src/lib.rs)). Removing restic therefore removes the system's only data-encryption layer, and it has to be rebuilt.

| Client lines simplified | ≈63 | 3-object LRU becomes sequential whole-segment reads |

The new work is not boilerplate. **Every hard item comes from chain semantics.** An incremental is useless without its base. A base cannot be deleted while dependants exist. Reclaiming space needs a full re-send. Restore must run strictly in order. Pool-to-pool tools such as zrepl solve these with pool-side primitives: a sender-side "replication cursor" bookmark, a "last-received-hold" on the receiver, and step holds that make `zfs destroy` fail on a needed base ([zrepl overview.rst](https://github.com/zrepl/zrepl/blob/master/docs/configuration/overview.rst)). A store of opaque segments has no pool, so the control plane would have to reimplement each primitive as metadata. The project's own earlier conclusion still holds: incremental chains can't be pruned remotely, and restic's prune model fits remote opaque storage better ([openzfs.md](../research_notes/Ceph%20and%20OpenZFS%20Rust%20port/openzfs.md)).

The ZFS-only design also gives up features that were built and tested this month. A tested partial read charged **37–39 KB for a 20 KB file in a 24 MiB pack**. Retention-based forget/prune reclaimed 8.4 MB with the newer snapshot still restorable. Dedupe within an account also goes ([docs/status.md](../docs/status.md)). None of these can be reproduced over streams: OpenZFS has no supported way to extract a file from a filesystem stream without receiving the whole chain into a pool ([zstream.8](https://raw.githubusercontent.com/openzfs/zfs/master/man/man8/zstream.8)), and "Deduplicated send is no longer supported" ([zfs-send.8](https://raw.githubusercontent.com/openzfs/zfs/master/man/man8/zfs-send.8)).

## Chains turn a grow-only set into an ordered log that needs compare-and-swap

Today the catalogue behaves like a grow-only set. Restic writes every file once, names it by the SHA-256 of its contents and never modifies it ([restic design.rst](https://raw.githubusercontent.com/restic/restic/master/doc/design.rst)). Concurrent or retried commits therefore commute, and two devices backing up at once produce extra objects, never a conflict. A ZFS chain is an ordered log instead. An incremental applies only if "the destination file system must already exist, and its most recent snapshot must match the incremental stream's source" ([zfs-receive.8](https://raw.githubusercontent.com/openzfs/zfs/master/man/man8/zfs-receive.8)). The match is checked by GUID: `drr_fromguid` and `drr_toguid` sit in the plaintext BEGIN record, and `drr_toguid` again in END ([zfs_ioctl.h](https://raw.githubusercontent.com/openzfs/zfs/master/include/sys/zfs_ioctl.h)). On mismatch, receive returns `ENODEV` ([dmu_recv.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/dmu_recv.c)).

OpenZFS checks this ordering only at receive time, which here means at restore, possibly years later. **The control plane therefore has to enforce it at commit.** It keeps one document per chain holding `head_toguid` and `head_seq`, and commits a stream with a conditional single-document update that matches `{head_toguid: s.fromguid, head_seq: s.seq−1}` and writes at `w: "majority"`. A unique index on `(chain_id, toguid)` completes the guarantee. Together they rule out gaps, forks, reordering and duplicates. MongoDB supports this pattern: a `findAndModify` with majority write concern on a uniquely identified document gives linearizable behaviour ([MongoDB findAndModify linearizable reads](https://www.mongodb.com/docs/manual/tutorial/perform-findAndModify-linearizable-reads/), [read concern linearizable](https://www.mongodb.com/docs/v8.0/reference/read-concern-linearizable/)). The update can join the transaction that already commits a segment and its catalogue entry, so it adds no extra round trip.

| Property | Restic today | ZFS stream chains |
|---|---|---|
| Catalogue semantics | Grow-only set of immutable, content-named objects | Ordered log per dataset with a single writer |
| Control-plane requirement | An atomic commit for each object | **Linearizable head CAS**, fork rejection, GUID linkage |
| Partition, control plane unreachable | No grants or commits, data safe (CP) | Same (CP). No change in CAP class |
| Partition mid-commit, outcome unknown | A retry produces a duplicate object, which is harmless | The CAS must be idempotent (same stream id equals success), or the retry is rejected as a fork |
| Multi-device | Several devices write to one repository | One chain per dataset per device |
| Rollback by a compromised control plane | Hides snapshots, caught by the client's remembered list | Truncates the chain, caught by the client's remembered head GUID (equivalent) |
| Semantics the control plane must understand | None: snapshot semantics live in the client | Chain dependency, retention by chain, repair priority by number of dependants |

Under Gilbert and Lynch's definition, a linearizable register cannot stay available during a partition ([Gilbert & Lynch 2002](https://www.comp.nus.edu.sg/~gilbert/pubs/BrewersConjecture-SigAct.pdf)). GlobalObject already accepts this for grants: "Control plane down: No new grants. Data stays safe but inaccessible" ([docs/architecture.md](../docs/architecture.md)). The real change is that **the control plane stops being semantics-free**. It becomes the arbiter of backup-chain validity, where today it holds a list of opaque names.

Two of the client's duties grow. While partitioned, the client must keep its last committed snapshot, or a bookmark of it, since `zfs send -i` accepts bookmarks ([zfs-send.8](https://raw.githubusercontent.com/openzfs/zfs/master/man/man8/zfs-send.8)). After the partition heals it sends one `-I` stream from the last committed GUID. GUIDs should also never reach the control plane in clear. If the client derives keyed hashes of `fromguid` and `toguid` under the account key, the control plane can still compare-and-swap on opaque edge identifiers. The real GUIDs, names and flags then live in a manifest that the client encrypts.

## Durability: similar expected loss, far worse worst case

The binomial model gives the probability that every segment a restore needs is online at once, for 1 TiB in 64 MiB segments, placement groups of 16, and 10 GiB of daily incrementals. **For a full restore of the latest state, a chain costs little extra.** At 1-of-3 and 90% host uptime, the probability falls from 0.359 (restic, or ZFS with no incrementals) to 0.266 with 30 incrementals. At 10-of-20 it stays above 0.99 even for year-long chains. For partial restores the gap is enormous: one file needs about one segment under restic (P ≈ 0.999) but the whole chain under ZFS (P ≈ 0.27). These all-at-once figures overstate stalls for long restores, since offline hosts come back. They matter more for ZFS, though, because `zfs receive` consumes the stream strictly in order and one missing segment stalls the pipeline ([cap_and_availability.md](../research_notes/ZFS%20send%20receive%20only%20interface/cap_and_availability.md), Q2).

| Measure (1 TiB base, 30 daily incrementals, 1-of-3 unless noted) | Restic | ZFS chain |
|---|---|---|
| P(all needed segments online), latest-state restore, p=0.90 | 0.359 | 0.266 |
| P(all needed segments online), one-file restore, p=0.90 | 0.999 | 0.266 |
| Snapshots made unrestorable by one random lost segment | Files in one 64 MiB pack only (~0.006% of data) | **27.5 of 31 (89%), each a whole dataset** |
| Chance the chain breaks in 1 year, at the sim's 0.045 lost segments/TB-year | ~3 MiB of file-level, repairable loss | **6.2%** (17.4% over 3 years) |
| Peak logical storage, keep 30 dailies, rebase every 30 days | 1,331 GiB | 2,345 GiB (**1.76×**) |
| Peak storage with yearly rebases | 1,331 GiB | 5,775 GiB (4.34×) |
| Cost of one 20 KB file restore | 37–39 KB | ≈1.43 TB, ≈6.6 days at 20 Mbps |
| Uplink time spent on monthly 1 TB fulls at 20 Mbps | None needed | 15.4% |

All rows are computed from stated assumptions ([cap_and_availability.md](../research_notes/ZFS%20send%20receive%20only%20interface/cap_and_availability.md), Q2–Q5). The simulator's report explicitly says not to advertise a durability figure from its loss rate ([docs/sim-report.md](../docs/sim-report.md)), so the chain-break probabilities illustrate scale and are not predictions.

The finding that matters is the **distribution of loss, not its mean.** `zfs receive` cannot skip a damaged record. A checksum failure at `DRR_END` returns `ECKSUM`, and a non-resumable receive then destroys what it created ([dmu_recv.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/dmu_recv.c)). Practitioners report the same: "All it takes is 1 single bit … and the entire stream is corrupt and unusable" ([FreeBSD forums](https://forums.freebsd.org/threads/how-to-make-a-zfs-backup.63042/), search excerpt). Restic, by contrast, has `repair snapshots`, which "will result in a limited amount of data loss" ([restic troubleshooting](https://raw.githubusercontent.com/restic/restic/master/doc/077_troubleshooting.rst)). Enterprise products reach the same conclusion about forward chains. When a health check finds a corrupt incremental, Veeam removes "that incremental restore point and the subsequent ones" and builds a new full ([Veeam health check](https://helpcenter.veeam.com/docs/vbr/userguide/backup_health_check.html?ver=13), search excerpt). Those products also assume a trusted, well-connected server that can build synthetic fulls. GlobalObject's keyless home hosts on slow uplinks are the worst environment for maintaining chains.

Storage overhead compounds the problem. Quota is charged on raw bytes, so 1.76× logical overhead at monthly rebases cuts the protected live data per contributed terabyte from about 267 GB to about 150 GB at 1-of-3. That widens the demand gap the project already reports: contributing 1 TB gives 267 to 400 GB, with days to upload and restore ([docs/status.md](../docs/status.md)). Short rebase intervals reduce storage overhead and fragility but use more uplink, and long ones do the reverse. **No rebase interval matches restic on both.**

## ZFS's own encryption cannot be the only layer

`zfs send -w` lets an untrusted machine hold the data without keys ([zfs-send.8](https://raw.githubusercontent.com/openzfs/zfs/master/man/man8/zfs-send.8)). That is why rsync.net and zrepl's "encrypted-send-to-untrusted-receiver" mode rely on it ([TrueNAS forum](https://www.truenas.com/community/goto/post?id=661449), search excerpt; [zrepl sendrecvoptions.rst](https://github.com/zrepl/zrepl/blob/master/docs/configuration/sendrecvoptions.rst)). But native encryption "will not encrypt metadata related to the pool structure, including dataset and snapshot names, dataset hierarchy, properties, file size, file holes" ([zfs-load-key.8](https://raw.githubusercontent.com/openzfs/zfs/master/man/man8/zfs-load-key.8)). Record headers carrying object numbers, offsets and lengths also stay in plaintext ([zfs_ioctl.h](https://raw.githubusercontent.com/openzfs/zfs/master/include/sys/zfs_ioctl.h)). Storing raw streams as they are would break the project's tested invariant "no plaintext on any disk or the control plane" for metadata. The stream's fletcher-4 checksum detects bit rot but does not authenticate: an attacker can recompute it, or zero the per-record checksums, which receive then skips ([dmu_recv.c](https://raw.githubusercontent.com/openzfs/zfs/master/module/zfs/dmu_recv.c)).

The bug record points the same way. Issue #12014, about snapshot corruption with encrypted datasets, stayed open from May 2021 to May 2025. It was closed by a fix to *non-raw* send of encrypted datasets, shipped in 2.2.8 and 2.3.3 ([#12014](https://api.github.com/repos/openzfs/zfs/issues/12014), [PR #17340](https://api.github.com/repos/openzfs/zfs/pulls/17340)). Encryption panics on receive remain open as of November 2026, for example #16065 ([GitHub](https://api.github.com/repos/openzfs/zfs/issues/16065)). zfs_autobackup's author notes that some send/recv bugs leave "the checksums … correct, but for the corrupt data" ([zfs-check wiki](https://github.com/psy0rz/zfs_autobackup/wiki/zfs-check)).

The design that follows from this is our own AEAD over every stream, built from an existing crate such as RustCrypto's STREAM construction or `age`, in line with the project's rule to use existing OSS for crypto. Keys would be derived with the Argon2id that is already a dependency. ZFS native encryption then becomes an optional inner layer. When the source dataset is natively encrypted, the client should require `-w`, which avoids the historically buggy non-raw-from-encrypted path and lets a future keyless helper receive the stream. It should also refuse streams with the DEDUP feature flag, record the sender's OpenZFS version and the stream's feature flags, and warn when a restore target is older. Older receivers reject streams whose feature flags they don't recognise ([zfs_ioctl.h](https://raw.githubusercontent.com/openzfs/zfs/master/include/sys/zfs_ioctl.h)), and "committed format" only promises that newer software reads older streams.

Licensing stays clean if users pipe `zfs send | globalobject send`. Our code then never links or runs CDDL code, which matches the project's rule that separately run tools are acceptable. No maintained Rust crate parses send streams: `zfskit` and `zrb` shell out to the CLI, and the libzfs FFI crates date from 2017–2023 ([crates.io](https://crates.io/api/v1/crates?q=zfs+send)). A small clean-room reader for the BEGIN and END records is enough to extract GUIDs and feature flags. Whether reproducing the CDDL header struct layouts creates licence obligations needs a short legal review before it ships.

## Phased plan: an additional input with bounded depth, never the only input

The audience settles the question of *only*. ZFS is first-class on FreeBSD, TrueNAS and Proxmox. Ubuntu's ZFS-root option is experimental, and its documentation recommends LUKS for encryption ([Ubuntu 26.04 docs](https://ubuntu.com/desktop/docs/en/26.04/reference/advanced-disk-setup-features/)). OpenZFS on Windows is still in release candidates ([openzfsonwindows releases](https://api.github.com/repos/openzfsonwindows/openzfs/releases)), and macOS builds lag upstream. A ZFS-only grid would exclude most home machines as data sources and as restore targets. A user whose laptop dies and is replaced by a Mac could not restore without a Linux VM. Demand from the ZFS niche is real but has not been well served. Two stream-to-object tools, z3 and zfsbackup-go, each gathered about 400 stars and then went stale. zfsbackup-go never implemented dependency-aware pruning ([zfsbackup-go](https://github.com/someone1/zfsbackup-go), [z3](https://github.com/presslabs/z3)). That makes ZFS streams a reasonable **second input** for homelab users, who are also GlobalObject's natural hosts, and a poor sole interface.

The most useful pattern from prior art is zfsbackrest's three levels. A `full` stands alone, a `diff` is an incremental from the latest full, and an `incr` is an incremental from the latest diff. "Child backups expire if the parent expires" ([zfsbackrest](https://github.com/gargakshit/zfsbackrest)). Depth is capped at three, so a restore replays at most three streams. Deletion becomes a simple cascade with no reference counting, and a lost `incr` segment damages one snapshot instead of everything after it. A lost `full` segment still damages every snapshot built on it, so full segments should get stronger redundancy (for example 1-of-5 or 10-of-20), and repair should prioritise them. The levels do not reduce the bytes needed for a latest-state restore when changes are all new data, because a late `diff` contains everything since the full. Diffs that repeat earlier changes also cost extra storage. The gains are bounded replay, bounded blast radius and simple expiry, not lower restore cost.

## Conclusion

The question assumed that streams would slim the system by handing chunking, snapshots and encryption to ZFS. The audit shows the opposite. Restic was never the bulk of the code; it was a thin adapter that kept backup semantics *out* of the control plane. Replacing it with chains pulls those semantics into MongoDB as an ordered log, and swaps restic's small, file-level, repairable losses for rare but total ones. Bandwidth and uplink are already GlobalObject's scarcest resources, and periodic full re-sends spend both. The useful result is a narrower one: ZFS streams fit well as an opt-in input for the homelab users who are also the grid's best hosts, provided the chain depth is capped, every stream is wrapped in our own AEAD, and the control plane's new compare-and-swap duty is designed in from the start rather than bolted on.

A secondary lesson is that the delete grace window (PR 5) has moved from "designed, not built" to blocking. Any design where one deletion can cascade through dependants, which bounded ZFS chains are by construction, should not ship before deletions can be undone.
